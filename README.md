# HR-4D：4D 毫米波雷达 3D 目标检测项目

## 一、我们为什么做这件事

本项目旨在基于 4D 毫米波雷达和神经网络，研发可用于真实道路环境的
3D 目标检测系统。

我们将以 OpenPCDet 为基础，复用成熟的 LiDAR 3D 检测方法，逐步完成
4D Radar 数据接入、模型适配、时序融合、性能优化和车端部署。在统一的
数据、标注和评测协议下，使纯 4D Radar 检测方案逐步接近 Hesai ATX
LiDAR 的任务级检测性能，并发挥毫米波雷达在雨、雾、黑夜等场景中的优势。

项目最终交付不是单个模型或论文指标，而是一套可复现、可评测、可部署、
可持续迭代的 4D Radar 3D 感知系统。

## 二、项目目标

### 近期目标

1. 建立可复现的 OpenPCDet 开发、训练和评测环境。
2. 接入公开 4D Radar 数据集和团队自采数据。
3. 完成 PointPillars、CenterPoint 等 LiDAR 方法的 Radar 基线适配。
4. 建立 ATX LiDAR 与 4D Radar 的同场景对照评测体系。
5. 完成数据可视化、错误分析和实验追踪工具。

### 中长期目标

1. 提升远距离、稀疏目标和遮挡目标的检测能力。
2. 利用 Doppler、RCS、SNR 和多帧信息构建 Radar 专用特征。
3. 探索 LiDAR Teacher 到 Radar Student 的知识蒸馏方案。
4. 探索原始 4D Radar 张量网络，突破点云后处理的信息上限。
5. 在目标 ODD 内达到约定的 ATX LiDAR 任务级对标指标。
6. 满足车端部署所需的延迟、算力、功耗和稳定性要求。

## 三、成功标准

“达到 ATX LiDAR 同等水平”必须通过统一评测协议判断，不能只比较单一
mAP 数字。所有 Radar 与 LiDAR 结果必须基于同一批同步采集数据和同一套
真值标注。

核心评价维度包括：

- 不同类别和距离段的 3D AP、BEV AP 与召回率；
- 固定误报率下的关键目标召回率；
- 中心位置、尺寸、朝向和速度误差；
- 晴天、雨天、雾天、夜间等场景的分组表现；
- 推理延迟、显存、算力、功耗和运行稳定性；
- 每小时误报数、关键目标漏检率和长尾问题数量。

## 四、技术原则

1. **先建立强基线，再研发复杂模型。**

   所有新方法必须与稳定、可复现的基线进行对照。

2. **数据质量优先于模型复杂度。**

   时间同步、坐标系、标定和真值错误必须优先处理。

3. **所有结论必须有实验支撑。**

   每项改动必须提供配置、指标、日志和消融结果。

4. **训练与评测必须可复现。**

   禁止只保留模型权重而缺失代码、配置、数据版本或环境信息。

5. **关注产品指标，不只关注公开数据集排名。**

   优先解决目标 ODD 内的真实失败案例。

6. **保持对 OpenPCDet 官方更新的可同步能力。**

   尽量减少对上游核心代码的无边界修改，项目功能应放在清晰模块中。

## 五、团队要求

### 基本要求

- 对自己的代码、实验结果和交付时间负责。
- 遇到阻塞及时公开，不隐藏风险，不用未经验证的结论推进决策。
- 尊重数据和实验事实；结果不理想时优先分析原因，不筛选性汇报指标。
- 文档、代码、配置和实验结果必须能够被其他成员理解和复现。
- 不得将私有代码、数据、模型、账号或密钥上传到公开平台。

### 代码协作要求

- 禁止直接向受保护的 `master` 分支提交开发代码。
- 每项工作使用独立分支，建议命名：
  - `feature/<内容>`：新功能；
  - `fix/<内容>`：问题修复；
  - `experiment/<内容>`：实验性改动；
  - `sync/<日期>`：同步 OpenPCDet 官方更新。
- 合并代码必须通过 Pull Request。
- Pull Request 必须说明目的、主要改动、验证方式、指标影响和已知风险。
- 至少一名其他成员完成代码审查后方可合并。
- 不得提交数据集、模型权重、训练输出、密钥和大体积临时文件。

### 实验要求

每次正式实验必须记录：

- Git 提交号与分支；
- 模型配置、数据版本和数据划分；
- 软件环境、GPU 型号和随机种子；
- 训练命令、评测命令和关键日志；
- 对照基线、结果表格和结论；
- 失败实验及失败原因。

无法复现或缺少对照实验的结果，不作为项目决策依据。

### 数据要求

- 原始数据只读保存，不得直接修改。
- 处理后数据、标签和标定文件必须有明确版本。
- 数据划分必须固定，避免训练集与测试集泄漏。
- 发现同步、标定或标注问题时，必须记录并通知相关负责人。
- 所有数据使用必须遵循授权、隐私和安全要求。

## 六、建议职责分工

| 责任域 | 主要职责 |
| --- | --- |
| 系统与产品 | 定义 ODD、对标指标、资源和里程碑 |
| Radar 信号处理 | 点云/张量输出、标定、噪声分析和质量提升 |
| 3D 感知算法 | 数据接入、检测基线、时序、蒸馏和模型优化 |
| 数据与平台 | 采集、同步、标注、版本管理和实验平台 |
| 部署与测试 | 推理优化、车端集成、场景回归和稳定性验证 |

每个任务必须有唯一负责人，同时指定至少一名可以接手的协作成员。

## 七、分支说明

- `master`：团队稳定主分支。
- `HR-4D`：4D Radar 项目研发分支。
- `upstream/master`：OpenPCDet 官方主分支，仅用于获取官方更新。

官方 OpenPCDet 更新不会自动进入本项目。同步上游更新前必须创建独立同步
分支，完成冲突处理、测试和 Pull Request 审核。
