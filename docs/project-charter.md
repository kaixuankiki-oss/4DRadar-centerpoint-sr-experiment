# 4D Radar 3D 检测项目章程

## 1. 项目目标

研发一套以 4D 毫米波雷达为推理输入的 3D 目标检测系统，并利用成熟的
LiDAR 3D 检测方法快速启动。在统一数据、统一标注和统一算力约束下，
逐步接近 ATX LiDAR 检测系统的任务级性能。

“同等水平”不能定义为单个公开数据集上的单一 mAP 数字，必须限定：

- ODD：道路类型、天气、昼夜、车速和目标类型；
- 感知范围与视场角；
- 目标类别、尺寸和遮挡等级；
- 允许的端到端延迟、算力、功耗和成本；
- 固定误报率下的召回率，以及定位和朝向误差。

ATX 官方规格包含最高 256 线、最高约 384 万点/秒、230 米量程
（10% 反射率）和 120 度 x 20 度视场。纯雷达在全场景下直接达到其几何
检测能力并不是合理的首期承诺。项目应先追求限定 ODD 内的任务级接近，
以及恶劣天气和运动目标上的优势。

## 2. 建议的验收定义

所有 Radar 与 LiDAR 指标必须来自同一批同步采集帧和同一套真值。

### 核心离线指标

- `3D AP` 与 `BEV AP`，按类别和距离段统计；
- 固定误报率下的召回率；
- 中心位置、尺寸、朝向和速度误差；
- 静态目标与动态目标分组结果；
- 晴天、雨天、雾天、夜间和强反射场景分组结果；
- 单帧与多帧模型的性能差异。

### 工程指标

- 端到端 P50 / P95 延迟；
- GPU/NPU 显存、算力占用与功耗；
- 丢帧、时间同步异常和传感器退化下的稳定性；
- 每小时误报数和关键目标漏检率。

### 建议的分阶段目标

以下比例均指同一评测协议下 Radar 相对 ATX LiDAR 基线的结果：

| 阶段 | 建议目标 |
| --- | --- |
| MVP | 完成闭环；Radar 基线可训练、可复现、可部署 |
| Alpha | 0-80 米核心类别的 Radar `3D AP` 达到 LiDAR 基线的 75%-80% |
| Beta | 0-120 米核心类别达到 85%-90%，恶劣天气下不弱于 LiDAR 基线 |
| Product Gate | 在产品 ODD 和固定误报率下达到已签署的任务级等效指标 |

这些比例需要在首次 LiDAR/Radar 对照实验后重新校准，不能作为未经数据
验证的产品承诺。

## 3. 技术路线

### 路线 A：Radar 点云适配 LiDAR 检测器

这是最快形成基线和工程闭环的路线。

1. 基于 OpenPCDet 接入自有 Radar 数据集。
2. 先复现 PointPillars，再复现 CenterPoint。
3. 将 Radar 点扩展为：
   `x, y, z, doppler, rcs, snr, timestamp, sensor_id`。
4. 加入车辆运动补偿和多帧时序累积。
5. 加入 Radar 专用的数据增强、噪声建模与置信度特征。

PointPillars 适合快速验证和低延迟部署；CenterPoint 适合作为主要精度
基线。不要直接把 Radar 的 RCS 或 Doppler 当作 LiDAR intensity 使用，
应单独编码并进行消融实验。

### 路线 B：原始 Radar 张量网络

点云通常经过 CFAR 或供应商后处理，弱目标信息可能已经丢失。若能够获得
距离、方位、俯仰、Doppler 维度的原始张量或中间特征，应并行研发张量
网络。

该路线应参考 K-Radar 和 RTNH/RTNH+ 类方法，重点研究：

- 原始张量稀疏化与高效编码；
- 俯仰维信息保留；
- Doppler 与静动态目标建模；
- 张量特征与 BEV 检测头的连接；
- 张量路线相对点云路线的真实收益和计算成本。

### 路线 C：LiDAR Teacher，Radar Student

ATX 不仅是对标传感器，也应作为训练期 teacher：

- 使用 ATX 模型生成软标签和高置信 proposal；
- 对齐 LiDAR 与 Radar 的 BEV 特征和目标中心；
- 使用 LiDAR 辅助自动标注，再由人工审核；
- 推理阶段保持 Radar-only，避免产品依赖 LiDAR。

## 4. 数据策略

### 公开数据启动

| 数据集 | 主要用途 |
| --- | --- |
| View-of-Delft | 快速验证 Radar 点云检测和 OpenPCDet 适配 |
| TJ4DRadSet | 验证多模态标定、Radar 点云和国内道路场景 |
| K-Radar | 验证原始 4D Radar 张量与恶劣天气检测 |

公开数据只能用于验证方法和工程链路，不能替代自有硬件数据。

### 自采数据必须包含

- 自研/目标 4D Radar 原始数据、张量和点云输出；
- 同步 ATX LiDAR；
- 相机、IMU/GNSS、车辆 CAN 和统一高精度时间戳；
- 内外参、温漂记录和标定版本；
- 目标 3D 框、类别、遮挡、截断和可见性属性；
- 天气、道路、车速、距离段和故障场景元数据。

数据团队必须优先解决时间同步、坐标系和标定质量。毫米级或毫秒级问题会
直接污染多帧融合、速度监督和 LiDAR teacher 蒸馏。

## 5. 推荐团队结构

若项目包含自研 Radar 硬件、信号处理和感知算法，建议设置以下责任域：

| 责任域 | 建议核心人数 | 主要交付 |
| --- | ---: | --- |
| 产品/系统负责人 | 1 | ODD、指标、成本、项目决策 |
| RF/天线/硬件 | 2-4 | Radar 硬件、天线设计、热与电气 |
| Radar DSP/信号处理 | 2-3 | 标定、FFT/波束形成、CFAR、点云/张量 |
| 3D 感知算法 | 3-5 | 基线、时序、蒸馏、Radar 专用网络 |
| 数据与标注平台 | 2-3 | 采集、同步、标注、数据版本 |
| 部署与性能工程 | 1-2 | 推理优化、车端集成、性能分析 |
| 测试与安全验证 | 1-2 | 场景库、回归、故障和安全验证 |

如果 Radar 硬件由供应商提供，仅开发感知算法，首期可由 5-8 人核心团队
启动：算法 3-4 人、数据/平台 1-2 人、部署 1 人、系统负责人 1 人。

## 6. 里程碑与退出条件

### Phase 0：定义与环境，2 周

- 签署 ODD、类别、范围、延迟和评测协议；
- 确认 Radar 是否提供原始 ADC、4D 张量和点云；
- 确认 ATX、Radar、相机、IMU 的同步与标定方案；
- 建立代码、数据、实验和模型版本规范。

退出条件：任何团队成员都能用同一脚本得到同一评测结果。

### Phase 1：公开数据基线，4-6 周

- 在公开数据复现 Radar PointPillars/CenterPoint；
- 记录每项输入特征和多帧累积的消融结果；
- 建立训练、评测、可视化和错误分析流水线。

退出条件：结果可重复，关键误差能够按距离、类别和场景检索。

### Phase 2：自采数据闭环，6-10 周

- 完成同步采集、标定、自动标注和人工审核；
- 在同一数据上训练 ATX LiDAR oracle 与 Radar 基线；
- 产出第一份 Radar/LiDAR 差距分析。

退出条件：明确差距来自数据、硬件、信号处理还是神经网络。

### Phase 3：性能突破，3-6 个月

- 多帧时序与运动补偿；
- Radar 专用编码器和噪声抑制；
- LiDAR teacher 蒸馏；
- 原始张量路线与点云路线对照；
- 围绕主要失败类型进行定向数据采集。

退出条件：达到 Alpha/Beta 指标，并证明提升可跨场景复现。

### Phase 4：部署与产品验证，持续进行

- 量化、编译和车端部署；
- 长尾场景、恶劣天气和传感器故障回归；
- 建立模型发布门禁与线上问题回灌。

退出条件：达到产品 ODD 下的性能、延迟、功耗和稳定性门禁。

## 7. 首批实验矩阵

第一轮实验必须控制变量，不应直接开始设计复杂新网络。

| 实验 | 输入 | 模型 | 目的 |
| --- | --- | --- | --- |
| L0 | ATX 单帧点云 | CenterPoint | 建立 LiDAR oracle |
| R0 | Radar 单帧 xyz | PointPillars | 最低 Radar 基线 |
| R1 | Radar 单帧完整特征 | PointPillars | 验证 Doppler/RCS/SNR |
| R2 | Radar 多帧完整特征 | PointPillars | 验证时序累积 |
| R3 | Radar 多帧完整特征 | CenterPoint | 验证模型容量收益 |
| R4 | Radar 多帧 + LiDAR 蒸馏 | CenterPoint | 验证 teacher 收益 |
| T0 | Radar 原始张量 | 张量基线 | 测量点云后处理的信息损失 |

## 8. 首要风险

1. **目标不可验收**：未限制 ODD 就承诺全面达到 ATX。
2. **硬件上限被忽略**：网络无法恢复从未被 Radar 观测到的稳定几何信息。
3. **只做公开数据论文指标**：公开数据与自有 Radar 域差异可能很大。
4. **标定与同步污染监督**：会让多帧融合和蒸馏产生错误结论。
5. **过早研发复杂模型**：没有强基线和错误分析时，无法证明改进来源。
6. **只看平均 mAP**：关键远距目标、固定误报率和长尾场景可能仍不合格。

## 9. 启动前必须确认的决策

1. 项目是自研 Radar 硬件，还是采购 Radar 后只开发感知算法？
2. Radar 能否输出原始 ADC、4D 张量、点云，以及各自帧率和数据率？
3. 产品 ODD、核心类别、有效距离和允许延迟分别是什么？
4. “达到 ATX 同等水平”是 Radar-only，还是允许 Radar + Camera？
5. 训练和车端部署分别使用什么 GPU/NPU？
6. 首期可以投入多少采集车辆、数据规模和核心研发人员？
